家里弱电箱的位置只够放一台机器，但我想要的东西有三个：软路由、NAS、还有一台随时能折腾的 Linux。PVE（Proxmox VE）是这三样装进一台 N100 的最省心方案——前提是把「直通」这两件事办明白。

直通（Passthrough）的意思是：把某个硬件从宿主机手里整个拿走，直接交给某台虚拟机。PVE 上最常见的两个直通对象就是核显和网卡。这篇写的是我在 N100 上跑通的完整流程，以及四个让我半夜重装系统的坑。

## 一、先做架构决策：核显给谁

这是整台机器最重要的一个决定，因为 **VFIO 直通是不可逆的**——核显一旦直通给某台虚拟机，宿主机和所有其他虚拟机就与它无缘了。

N100 的核显（UHD Graphics）在 NAS 场景里的价值就是硬解：Jellyfin 转码、Immich 机器学习加速、监控录像解码。我的选择是：

- **核显不直通**。宿主机 + LXC 容器共享使用，Jellyfin 装在 LXC 里，直接挂载 `/dev/dri` 就能硬解。性能损耗几乎为零，配置五行。
- **网卡直通给 OpenWrt**。软路由对网卡的要求是独占和低延迟，且它需要至少两个口（WAN/LAN），直通两张 2.5G 物理网卡最干净。

「共享核显」比「直通核显」好，这是我要纠正的第一个网传误区。很多教程上来就教你 VFIO 直通核显给 Windows 虚拟机，那是给「单机独占」场景准备的；家用 NAS 场景里，直通等于把最值钱的硬件锁进一个笼子。

## 二、直通前的三件准备

**1. BIOS 里开 VT-d / IOMMU。** N100 的 BIOS 菜单里叫「Intel VT-d」或「VMX/VT-x + VT-d」。只开 VT-x 不开 VT-d，虚拟机能跑但设备直通不了。

**2. 确认内核参数。** PVE 8 之后 `intel_iommu=on` 默认生效，但旧镜像不一定。检查方法：

```bash
dmesg | grep -e DMAR -e IOMMU
# 看到类似 "DMAR: IOMMU enabled" 就算就绪
```

**3. 看 IOMMU 分组。** 直通的前提是你要的那个设备在独立分组里（或者同组没有别的关键设备）：

```bash
for d in /sys/kernel/iommu_groups/*/devices/*; do
  echo -n "$(basename $(dirname $d)) $(basename $d) "
  lspci -nns ${d##*:} | cut -d' ' -f2-
done | sort -n
```

## 三、坑一：所有设备挤在一个 IOMMU 组

N100 是 SoC，PCIe 通道少，我第一次看分组输出时心凉了半截：核显、网卡、NVMe、USB 控制器全在 group 0。这意味着按正规流程一台虚拟机都直通不了。

网上通行的解法是内核参数 `pcie_acs_override=downstream,multifunction` 强行拆组。**这个参数的本质是骗过内核的隔离检查**：硬件上这些设备仍然共享一条通道，虚拟机理论上可以越权读写同组其他设备的内存。

我的取舍：家用环境，机器里没有敌对租户，接受。但加了这个参数之后，我把「出问题先怀疑 ACS」写进了自己的排障笔记——有一次 Jellyfin 转码莫名卡死，绕了一大圈，最后是直通的网卡在重置时把共享通道拖挂了。**软路由和网络设备直通时尤其注意**：OpenWrt 重启网卡，宿主机的 NVMe 可能跟着抽风。

## 四、坑二：核显直通给 VM 后，转码还是走 CPU

如果你最终还是决定直通核显（比如要在 Windows 虚拟机里用），别以为「直通成功」就完事了。我当时的症状：虚拟机里能看到核显，Jellyfin 也能选 Intel QSV，但一转码 CPU 就飙满，GPU 占用纹丝不动。

原因是虚拟机里的 Jellyfin 进程没有 `/dev/dri/renderD129` 的访问权限，QSV 初始化失败后静默回落到 CPU 软解。修法是把用户加进 `render` 和 `video` 组：

```bash
usermod -aG render,video jellyfin
# 容器/虚拟机重启后再用这个验证：
sudo -u jellyfin vainfo
# 能列出 VA-API profile 才算真正用上了硬解
```

`vainfo` 报错就是最终答案，不要相信 Jellyfin 设置页里那个「硬件加速：已启用」——它只代表你选了下拉框。

## 五、坑三：把管理口直通出去，PVE 失联

这是我交过最贵学费的一个坑。PVE 的网页管理依赖宿主机的网络，而直通网卡给 OpenWrt 之后，宿主机自己的流量就得走 OpenWrt 转发——**虚拟机挂了，宿主机跟着失联**，我又没在机器旁边，只能等下班回家插显示器。

正确姿势有两种：

1. **留管理口**：机器如果有三个以上网口，留一个给 PVE 本体，不参与直通、不走 OpenWrt。
2. **USB 网卡当保险**：花二十块买一个 USB 千兆口，pve 本体绑它，平时不用，救急时插上就有管理通道。

另外直通 OpenWrt 的网卡要用「宿主机不加载驱动」的绑定方式（VFIO），配置文件里加 `softdep` 黑名单对应驱动（RTL8125 是 `r8169`），否则宿主机抢先用上了驱动，虚拟机那边就报 `No IOMMU found`。

## 六、坑四：直通配置改完，机器开不了机

改内核参数（`/etc/kernel/cmdline` 或 grub）和驱动黑名单之后重启，机器卡在启动阶段——大多数是参数打错字或黑名单写错了驱动名。**改这类文件前先在 PVE 控制台验证一遍当前能否进入救援模式**，手边备一个 Ventoy U 盘启动盘。

我的习惯是：每次只改一个文件，改完立刻 `proxmox-boot-tool status` 和 `update-initramfs -u -k all` 验证，再重启。一次改三处的代价就是不知道该回滚哪一处。

## 七、最终形态与性能账

现在的结构：

| 角色 | 形态 | 说明 |
| --- | --- | --- |
| PVE 宿主机 | 管理面 + 核显持有者 | 网页管理、USB 网卡兜底 |
| OpenWrt | VM，2 × 2.5G 直通 | 软路由，独占网卡 |
| NAS 服务 | LXC 群（Jellyfin / Immich / qBittorrent） | 共享核显 + ZFS 数据盘 |
| 备用 Linux | 随手开的 VM | 折腾测试用 |

内存 16G 单通道不变，实测 Jellyfin 4K 转码走核显时 CPU 占用 15% 上下，直通与否对它无影响——因为核显根本没直通，一直在宿主机手里。

**这台机器上唯一值得直通的就是网卡。** 把直通用在刀刃上，其余场景共享，是 N100 这种小机器上最稳的姿势。如果你想看硬解本身怎么配，Jellyfin 那篇写得更细；远程访问的部分在 Tailscale 那篇里。
